## Запуск бота

```bash
cd bot
pip install -r requirements.txt
python main.py
```

Токен сейчас зашит по умолчанию в `config.py`, как ты и просил — для
тестирования дополнительная настройка не нужна, бот заработает сразу.
Когда закончишь тестировать: отзови токен через @BotFather → `/revoke`,
скопируй `.env.example` в `.env` и впиши туда новый токен — `config.py`
подхватит его автоматически (`.env` уже в `.gitignore`, в git не попадёт).

## Что было исправлено

### 1. Баг с минималкой (главная жалоба)
В `saveSettings()` (теперь `js/api/settings.js`) использовался:
```js
.update({ value }).eq('key', key)
```
Если строки с таким `key` ещё не было в таблице `settings` — `update`
обновлял 0 строк и **не считал это ошибкой**. В интерфейсе всё выглядело
так, будто сохранилось, а по факту в базе ничего не менялось. При
перезагрузке / открытии формы заказа код заново читал настройки из
Supabase, находил пустоту и откатывался на дефолт (100 ₽ / 50 Stars).

**Исправлено:** `upsert(rows, { onConflict: 'key' })` — создаёт строку,
если её нет, и обновляет, если есть.

### 2. Скрытый баг вкладки "Админ"
В HTML у `#page-admin` было `style="display:none"`, а JS отдельно делал
`style.display = 'block'`. Инлайн-стиль всегда побеждает CSS-классы —
поэтому после первого захода в админку эта вкладка могла оставаться
видимой поверх остальных при переключении между вкладками. Убрал
инлайн-стиль и лишний JS-код: теперь видимость управляется только
классом `.active`, как у всех остальных вкладок.

### 3. Баннер миграции был "мёртвым" кодом
Разметка и CSS для баннера были в проекте, а JS-логики не было вообще —
баннер никогда не появлялся, кнопка закрытия ничего не делала.
Реализовал полноценно (`ui/migrationBanner.js`), включается флагом
`MIGRATION_BANNER.enabled` в `config.js`.

### 4. Мелкая неточность с нулевыми значениями
Старый код кое-где читал настройки как `settings.steam_min || 100` —
это трактует явно заданный `0` как "не задано". Новая функция
`withDefaults()` в `api/settings.js` использует object spread, поэтому
корректно отличает "значения нет вообще" от "значение равно 0".

## Важно — безопасность (не мелочь!)

**Проверка "это админ" (`user.id === ADMIN_TELEGRAM_ID`) происходит
только в браузере** — она прячет кнопку "Админ" в интерфейсе, но
**не защищает саму базу данных**. Если в Supabase у таблиц
`settings`, `orders`, `users` настроены разрешающие RLS-политики
(или RLS вообще выключен), то любой человек может открыть консоль
браузера, взять твой anon key прямо из `config.js` (он и должен быть
публичным, это нормально для Supabase) и напрямую отправить запрос на
изменение цен или чужих заказов — в обход всего интерфейса.

Что сделать:
1. Зайди в Supabase → Authentication / Table Editor → Policies.
2. Для таблицы `settings`: разреши `SELECT` всем, а `UPDATE`/`INSERT` —
   никому напрямую из клиента (либо через выделенную server-side
   функцию/Edge Function, которая сама проверяет Telegram `initData`).
3. То же самое для `orders` — обычный пользователь может создавать
   свои заказы, но не должен иметь возможность менять статус чужих.

Без этого шага любые "проверки на клиенте" — это просто UI, а не
защита.

### Если сохранение настроек в админке падает с 401

Это прямое следствие пункта 2 выше: если ты (или кто-то) уже закрыл
`UPDATE`/`INSERT` на таблице `settings` для анонимного ключа — молодец,
это правильно с точки зрения безопасности, но админ-панель в этом
проекте пишет настройки **тем же самым anon-ключом прямо из браузера**,
без отдельного сервера. Поэтому запись оказывается заблокирована и для
настоящего админа тоже — читать (`SELECT`) продолжает работать, а
писать нет, отсюда и путаница "то работало, то перестало".

Два варианта:

**Быстрый (для теста/MVP).** Разреши запись в `settings` анониму — это
приемлемо, если единственное, что там лежит, это цены/минималки, а не
что-то критичное. В Supabase → SQL Editor:
```sql
create policy "anon can write settings"
on settings for all
to anon
using (true)
with check (true);
```

**Правильный (когда будешь готов).** Держи `settings` закрытой для
анонимного ключа и добавь Supabase Edge Function (или простой сервер),
которая принимает Telegram `initData`, сама проверяет подпись и
`user.id === ADMIN_TELEGRAM_ID`, и только после этого пишет в базу
через `service_role` ключ. Тогда `saveSettings()` в `admin.js` будет
дергать не таблицу напрямую, а эту функцию.

`js/api/settings.js` теперь возвращает `{ success, error }` вместо
`true/false` — при ошибке в статусе админки сразу видно причину, а не
только "Ошибка сохранения. Проверьте консоль."

### Если покупка падает с "Не удалось создать заказ"

Та же самая история, только с таблицей `orders`: если RLS включён, а
политики `INSERT` для анонимного ключа нет — заказ не создаётся вообще,
хотя баланс на экране мог на секунду списаться (потом возвращается
обратно, деньги не теряются). Теперь `createOrder()` в `api/orders.js`
возвращает `{ order, error }`, и настоящая причина сразу показывается
в тосте об ошибке — не нужно открывать консоль браузера (F12), чтобы
понять, что произошло.

Быстрый вариант для теста/MVP — та же логика, что и для `settings`:
```sql
create policy "anon can create orders"
on orders for insert
to anon
with check (true);

create policy "anon can read orders"
on orders for select
to anon
using (true);
```
Обрати внимание: нужны **обе** политики — `INSERT`, чтобы заказ вообще
создавался, и `SELECT`, потому что код сразу читает обратно только что
созданную строку (`.select().single()` после `insert`), чтобы получить
её `id` и `status` — без политики на чтение Supabase создаст заказ, но
тут же откажется вернуть его, и в интерфейсе это будет выглядеть как
та же самая ошибка.

Для продакшена — тот же принцип, что описан выше для `settings`:
правильное решение — Edge Function с проверкой Telegram `initData`,
а не открытый анонимный доступ на запись.

### Если покупка падает с "Could not find the 'account_data' column..."

Это не баг в коде — это значит, что твоя таблица `orders` в Supabase
физически создана без одной или нескольких колонок, которые ожидает
код (например, её создавали вручную раньше, до того как в проект
добавили поле `account_data`). Supabase (точнее PostgREST) в таком
случае честно говорит "такой колонки нет", а не создаёт её сама.

Открой Supabase → SQL Editor и выполни (безопасно выполнять повторно,
ничего не сломает, если колонка уже есть):
```sql
alter table orders add column if not exists user_id bigint;
alter table orders add column if not exists product text;
alter table orders add column if not exists amount numeric;
alter table orders add column if not exists price_rub numeric;
alter table orders add column if not exists account_data text;
alter table orders add column if not exists status text default 'pending';
alter table orders add column if not exists created_at timestamptz default now();
```
После этого подожди секунд 10–15 — Supabase иногда обновляет
"schema cache" не мгновенно — и попробуй купить ещё раз. Если не
помогло — зайди в Supabase → Settings → API и нажми "Reload schema
cache" вручную (или просто сохрани там любую настройку — это тоже
триггерит обновление).

## Изменения в этом обновлении

1. **Мигание окна согласия у уже согласившихся пользователей.**
   `#consentOverlay` был виден по умолчанию (без класса `hidden`) —
   пока грузился профиль из Supabase, он на долю секунды показывался
   всем, даже тем, кто уже принял условия. Добавлен экран загрузки
   (`#loadingOverlay`, `js/ui/loadingOverlay.js`) — он закрывает собой
   весь период загрузки, и после него сразу показывается ровно то, что
   нужно конкретному пользователю, без мигания и рывков.

2. **Символ `@` в поле Stars теперь нельзя стереть.** Раньше это было
   просто начальное значение поля — его можно было выделить и удалить
   целиком. Теперь `enforceStarsPrefix()` в `orderModal.js` возвращает
   `@` обратно, если пользователь его стирает; удалить можно только то,
   что после него.

3. **Подтверждение заказа — теперь во вписанной в дизайн модалке**,
   а не в системном попапе Telegram (`tg.showPopup`). Новая модалка
   `#orderConfirmModal` показывает "Вы уверены, что хотите создать
   заказ на сумму ..., получив ... ?" с кнопками "Да"/"Нет" в общем
   стиле приложения.

4. **После подтверждения покупки:** модалка заказа закрывается,
   появляется тост "Заказ создан и передан в обработку"
   (`js/ui/toast.js`), заказ сразу пишется в Supabase со статусом
   `pending` и в этом же виде появляется в истории профиля с плашкой
   статуса **"В обработке"**.

5. **Статусы заказов теперь синхронизируются с админкой.** Раньше
   локальная история в профиле обновлялась только в момент покупки и
   никогда не узнавала, что админ пометил заказ как "выполнен" или
   "отклонён". Теперь `refreshHistoryFromServer()` (в `history.js`)
   подтягивает актуальные заказы из таблицы `orders` при запуске
   приложения и при каждом открытии вкладки "Профиль" — статус в
   истории обновляется автоматически. В таблицу истории добавлена
   отдельная колонка "Статус" с цветной плашкой (жёлтая — в обработке,

   теперь возвращает `{ order, error }` вместо голого `null` — реальная
   причина (чаще всего RLS-политика на таблице `orders`, см. раздел

## Реальные крипто-платежи — план на следующий этап

Сейчас `generateDepositAddress()` в `depositModal.js` — по-прежнему
заглушка (адрес с префиксом `DEMO-`, ничего реального не создаётся).
Баннер "тестовый режим" в модалке пополнения оставлен намеренно и
не должен убираться, пока не появится реальный механизм подтверждения
оплаты — иначе люди будут отправлять настоящую криптовалюту в никуда.

Договорились делать свой мониторинг блокчейна (без стороннего платёжного
шлюза), чтобы:
- комиссия для сервиса была ~0% (платит только отправитель — сетевую
  комиссию, тебе — только хостинг);
- можно было хостить бесплатно (Railway/Fly.io free tier и т.п., там же,
  где уже крутится бот);
- обработка была "почти мгновенной" за счёт опроса (polling) блокчейна
  каждые 15–30 секунд (полноценных вебхуков в этой схеме не будет).

Кратко, как это будет устроено:
- **TON** — самый удобный из трёх: у переводов есть поле "комментарий",
  туда можно класть ID заказа и однозначно сопоставлять платёж с
  конкретным пользователем/заказом. Читается через toncenter/tonapi.
- **TRX и USDT (TRC-20)** — сложнее: комментариев в переводах нет,
  поэтому либо генерируем отдельный адрес на каждый платёж, либо просим
  оплатить не круглую сумму (например, 100.0623 ₽-эквивалент) для
  идентификации плательщика. Читается через TronGrid API.
- Весь мониторинг будет отдельным процессом (скорее всего расширение
  `bot/`), который раз в 15–30 сек проверяет новые платежи и обновляет
  баланс пользователя в Supabase — сама mini-app не будет обращаться к
  блокчейну напрямую.

Это отдельный этап работы, начинается после того, как весь текущий
функционал будет полностью стабилен.
